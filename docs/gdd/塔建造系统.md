# 塔建造系统

> 状态：重构实施基线
> 最后更新：2026-08-03
> 规则来源：当前可运行实现、GameScene 六层 Authoring 与《核心架构重构计划》

## 概述

人类单位的共同目标是自下而上完成巴别塔。塔由场景 Authoring 决定层数和建造点，不再使用旧草案中的“固定十层、到达即填满一个槽位”模型。

玩法 Runtime 只处理层、建造点、施工进度和塔完成规则；Sprite、动画、Transform 和进度条属于 Unity Presentation。所有施工贡献都先写入同 Tick 的 BuildWorkBuffer，在死亡结算之后统一提交。

## 当前六层 Authoring 基线

层顺序固定为从底到顶：

| Runtime 层索引 | Scene Path | 建造点数 | Gateway 数 | 当前塔片 |
| --- | --- | ---: | ---: | --- |
| 1 | Path_01 | 8 | 1 | tower_t6_* |
| 2 | Path_02 | 7 | 1 | tower_t5_* |
| 3 | Path_03 | 6 | 1 | tower_t4_* |
| 4 | Path_04 | 6 | 1 | tower_t3_* |
| 5 | Path_05 | 5 | 1 | tower_t2_* |
| 6 | Path_06 | 4 | 0 | tower_t1_* |

合计 36 个建造点、5 个 Gateway、2 个 SpawnPoint。该结构由构建前校验器保护；层数组必须显式按底到顶绑定，不能依赖对象查找顺序。

## 核心规则

1. 只有当前最低的未完成层接受施工。
2. 同一个未完成建造点可以被多名 Builder 同时选择，不存在独占预约。
3. Builder 到达目标后等待自身 BuildTime，到时一次性提交 BuildContribution，不是每 Tick 连续增加。
4. 贡献成功提交后才消耗一次 BuildCharges。
5. 等待期间若目标已被其他单位完成，本次不消耗 Charge，单位重新选择目标。
6. 普通 Builder 从当前层未完成点中使用本局 Seed 随机选择。
7. Scout 优先选择未完成 Gateway；无可用 Gateway 时再使用普通选择规则。
8. 单位的 Charge 耗尽后退出模拟并归还 View 池。
9. 当前层所有建造点完成后立即开放上一层；顶层完成即塔完成。
10. 新生成实体从下一 Tick 才参与 Brain、移动、战斗和施工。

## 中央 Tick 顺序

与施工有关的固定顺序如下：

~~~text
Human Brain（每 6 Tick）
→ Navigation / Work Intent
→ Abilities
→ Combat Damage
→ Death / Despawn / DeathReward
→ Babel BuildWork
→ Progression
→ Encounter / Spawn
→ Run Rules
~~~

关键约束：

- 死亡先于施工。BuildWorkBuffer 结算时必须再次验证 EntityHandle(index, generation) 仍存活；本 Tick 已死亡单位不能施工。
- 多次致死伤害只确认一次死亡、一次击杀和一次经验奖励。
- 如果同一 Tick 内塔完成且倒计时归零，塔完成优先，玩家失败。
- Gameplay 不使用 UnityEngine.Random；目标选择必须来自本局 IRandomSource。
- 暂停、升级选择、胜负结算期间不执行模拟 Tick，也不积压 Gameplay Command。

## Runtime 数据模型

### BabelDefinition

Editor ContentCompiler 从 Scene Authoring 编译不可变定义：

- 从底到顶的层顺序；
- 每层建造点数量；
- Gateway 标记；
- 每个建造点所需进度；
- Presentation 使用的稳定 View ID。

当前默认结构为：

~~~text
BuildPointCounts = [8, 7, 6, 6, 5, 4]
GatewayCounts    = [1, 1, 1, 1, 1, 0]
~~~

### BabelState

每局独立持有：

- 当前活跃层；
- 各建造点当前进度和完成状态；
- 各层完成状态；
- 总完成度；
- 塔是否已完成。

它不保存 GameObject、Transform、SpriteRenderer 或静态事件。

### BuildWorkRequest

每条施工请求至少包含：

~~~text
Source: EntityHandle
LayerIndex: int
BuildPointIndex: int
Amount: int
~~~

结算结果分为成功、目标已完成、层未激活、来源已死亡或句柄已过期。只有成功结果可以扣除 Charge。

## 与其他模块的边界

| 模块 | 输入 | 输出 |
| --- | --- | --- |
| Humans / Brain | Babel 只读状态、单位职业 | 目标选择 |
| Navigation | 目标和移动状态 | 到达/工作意图 |
| Combat / Death | DamageBuffer | 存活状态、DeathReward |
| Babel | BuildWorkBuffer | 点/层/塔完成状态 |
| Progression | DeathRewardBuffer | 信仰、等级、升级选择 |
| Encounter | WaveCatalog、RunClock | SpawnRequest |
| Presentation | ReadModel、表现事件 | 只更新 View，不回写玩法状态 |

## Unity Presentation

- Scene 中的建造点对象只是 BabelPointView，根据 ReadModel 或表现事件切换隐藏、施工中、已完成视觉。
- BabelPresenter 批量同步 36 个点，不允许每个点用独立玩法 Update。
- Gateway 是 Authoring 数据，不由 Sprite 名称或层级名称推断。
- Scene/Prefab 移动必须保留 .meta；构建前检查 Missing Script、重复引用和层顺序。

## 验收用例

### EditMode

- 两名 Builder 可同时选择同一点。
- 等待完整 BuildTime 后只提交一次进度块。
- 成功施工才扣 Charge。
- 目标被抢先完成时不扣 Charge并重新选择。
- Scout 优先 Gateway。
- 已死亡或旧 generation 的来源施工被拒绝。
- 同 Tick 多次施工按稳定顺序结算且不会重复完成。
- 36 个点逐层完成后顶层触发失败。
- 塔完成与计时归零同 Tick 时失败优先。
- 固定 Seed 下目标序列完全一致。

### PlayMode / 内容校验

- GameScene 恰好一个 RunRoot、Tower Authoring 和主摄像机。
- 六层点数为 [8,7,6,6,5,4]，Gateway 为 [1,1,1,1,1,0]。
- 36 个 BuildPoint 引用非空且不重复，2 个 SpawnPoint ID 非空。
- Pool 复用后建造目标、血条、Buff、动画和协程状态全部重置。
- 连续两局不存在旧点状态、旧实体或旧订阅。

## 已废弃的旧草案假设

以下内容不再作为实现依据：

- 固定 10 层和 55 个槽位；
- 单位到达即完成一个槽位并立即消失；
- 普通槽全部完成后才允许选择 Passage；
- 使用“最近槽位”作为所有职业的固定选择策略；
- 依赖 GameLoopManager、静态 OnActiveLayerChanged 或每敌人回调推进塔状态；
- 用 Time.timeScale 或帧顺序决定同 Tick 结算结果。

若未来改变层数、Gateway 策略或块提交规则，必须先更新本文件、Content Definition 和自动化测试，再修改 Runtime。
